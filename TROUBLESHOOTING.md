# Troubleshooting log

## ST3215 servo: no response on the bus (RESOLVED — driver bug, not hardware)

**Symptom:** after wiring the ST3215 servo through a Waveshare Bus Servo Adapter (A) into the SKR Pico's `Laser` connector (IO0/IO1, see `PINOUT.md`), `scanner_rig.py`/`st3215.py` got `OSError: no reply` on every call — `ping()`, `read_position()`, `set_goal_deg()`.

**Root cause:** `st3215.py`'s `write_register`/`read_register` unconditionally drained a "self-echo" after every UART write, copying the pattern from `tmc2209.py` where that's correct — on the TMC2209 bus, TX is wired straight into RX through a resistor, so every transmitted byte genuinely echoes back and must be drained before the real reply. The Waveshare adapter is a different kind of circuit: it's a real transceiver, so our TX and RX stay electrically separate right up to the adapter, and there is **no self-echo on this bus at all**. The servo replies within microseconds - faster than the bogus "echo" read's timeout - so that drain call was silently swallowing the servo's real reply every single time, then timing out waiting for a second reply that would never come. This happened identically regardless of servo unit, cable, jumper position, or baud rate, which is exactly why none of those varied.

**How it was found:** extensive hardware-side diagnosis (MCU-pin loopback test, cable swap, full baud/ID sweep, independent verification against the official Waveshare `scservo_sdk` run directly against the adapter over USB) ruled out every piece of hardware in the chain, including the servo units themselves - see the diagnostic steps below, still accurate as a record of what was checked, even though the conclusion drawn from them at the time was wrong. The actual bug was found by comparing against a working third-party MicroPython driver, which didn't drain any echo unless an explicit half-duplex `dir_pin` was configured (see `sts3215.py` for that reference implementation) - the SKR Pico/Waveshare-adapter setup here doesn't use one.

**Fix:** removed the erroneous `self._read_exact(len(pkt))` call after `self.uart.write(pkt)` in `st3215.py`'s `_txrx`. Confirmed working end-to-end through the SKR Pico afterward: `ping()`, `read_position()`, and `set_goal_deg()` all succeed and the servo physically moves.

**Diagnostic steps taken along the way (all correctly ruled out hardware, which was never actually the problem):**

1. **Adapter jumper position** — confirmed `A` (external-MCU UART mode) for SKR Pico use, `B` for direct-PC/USB use. Both work correctly with the fixed driver; the earlier confusion was largely from having the jumper in the wrong position during a couple of PC-direct isolation tests, compounding the real (driver) bug.
2. **Adapter power** — power LED lit, confirmed powered.
3. **TX/RX crossing** — confirmed correct (SKR Pico TX → adapter RX, SKR Pico RX → adapter TX).
4. **MCU-side loopback test** — shorted IO0/IO1 together directly at the SKR Pico connector, sent raw bytes over `UART(0, tx=Pin(0), rx=Pin(1))`, got them back. Confirmed the RP2040 pins/UART0 hardware healthy (this was always true; the bug was downstream in application-level packet handling, not the hardware UART).
5. **Baud rate / full ID sweep**, **cable swap**, **servo swap**, **independent official-SDK verification over direct USB** — all done, all pointed at "the servo/adapter doesn't answer", because the *same class of bug* (an extra blocking read before reading the real reply) doesn't exist in the official SDK or in a correctly-written driver, so those channels worked once the jumper was set correctly - which is what made it look like a hardware fault specific to the SKR-Pico path.

## Y/Z sensorless homing (StallGuard/DIAG): no trip detected (IN PROGRESS — several real bugs fixed, final verification pending real hardware assembly)

**Symptom:** `Y HOME`/`bounce_task`'s DIAG-based stall detection never tripped, at any `SGTHRS` from 0 to 254, under either stealthChop or spreadCycle, at 400mA or 800mA, at 150 or 500 steps/sec, and with the axis genuinely blocked by hand (via the gear, not the bare motor shaft) for many seconds at a time.

**Multiple real bugs found and fixed along the way, in the order discovered:**

1. **`asyncio.sleep_us` doesn't exist in this uasyncio build** — a separate, earlier bug (see git history) that meant `x_task`/`bounce_task` had never actually run through the real event loop before; fixed by switching to `sleep_ms` plus a brief blocking `time.sleep_us` just for the STEP pulse width.
2. **stealthChop makes StallGuard noisy.** Raw `SG_RESULT`, read live during free spinning, bounced erratically between 0 and 24 under stealthChop - polling it directly (the first approach tried) was unusable. Switching to spreadCycle during homing (`motor.enable_uart_mode(spreadcycle=True)`, restored afterward) cleaned this up to a stable 0-4 range. This matches the Voron sensorless-homing guide, which mandates `stealthchop_threshold: 0` (i.e. spreadCycle) for exactly this reason.
3. **`TCOOLTHRS` direction was backwards.** It was first set to a *low* value (3000) on the theory that this "activates StallGuard at low speed." The Trinamic datasheet phrase "lower threshold velocity for switching **on**" actually means the opposite: TCOOLTHRS is a *minimum* speed, and StallGuard/DIAG is active *above* it. A low TCOOLTHRS require a *high* speed to activate - at our actual bounce/home speeds this most likely disabled DIAG outright. Confirmed against [Chr157i4n/PyTmcStepper's `_tmc_stallguard.py`](https://github.com/Chr157i4n/PyTmcStepper/blob/main/src/tmc_driver/_tmc_stallguard.py), which derives `TCOOLTHRS` from a *minimum* homing speed. Fixed by setting it back to the register maximum (`0xFFFFF`), i.e. "active at any practical speed."
4. **Reduced current improves StallGuard's usable signal during homing** specifically - the Voron guide uses roughly half the normal run current (~0.49A) just for the homing move, restored afterward. Implemented as `HOME_CURRENT_MA`, applied/restored in `home_axis`'s `try/finally` alongside the spreadCycle toggle.
5. **Home speed was too low.** 150 steps/sec (at 16 microsteps, under 10 full steps/sec) doesn't give StallGuard enough real velocity for a clean reading. Raised the default to 500.
6. **Jumper cap position is still unresolved - a false lead, corrected.** A `Y-DIAG` pin-level check (no pull / `PULL_UP` / `PULL_DOWN` all reading a stable `0`) suggested the pin was actively driven rather than floating, so `Y-DIAG`/`Z-DIAG` jumper caps were physically swapped as a test. Afterward `y_diag.value()`/`z_diag.value()` did start reading live and tracking `SGTHRS` changes - but it turned out the caps had actually been moved to the two *other*, otherwise-unused DIAG headers (`X-DIAG`/`E0-DIAG`), not swapped between `Y-DIAG` and `Z-DIAG` as intended, leaving `Y-DIAG`/`Z-DIAG` uncapped. With no jumper connecting DIAG to the STOP header at all, `Y-STOP`/`Z-STOP` should just be floating GPIOs - the "live-looking" readings that correlated with `SGTHRS` and motor activity were almost certainly EMI/crosstalk from the adjacent STEP pulses on a floating pin, not a real StallGuard signal. **This result is not trustworthy and should be disregarded.** The caps need to go back on `Y-DIAG`/`Z-DIAG` specifically (confirmed by an earlier photo of the correct position) before re-testing.

**Update after correctly reseating the caps on `Y-DIAG`/`Z-DIAG`:** idle `y_diag.value()` now correctly reads `0` (matching `z_diag`, and no longer the stuck-`1` seen with the caps in the wrong (empty) headers). Comparing against [AndreaFavero71/stepper_sensorless_homing](https://github.com/AndreaFavero71/stepper_sensorless_homing/blob/main/src/board_V2/stepper.py) - which computes its expected StallGuard baseline as *proportional to step frequency* (`min_sg_expected = 0.15 * stepper_freq`), at speeds of 400-1200 Hz **full steps** - suggested our homing speed was still far too slow: 500 "steps/sec" in this codebase means *microstep* pulses at 16 microsteps, i.e. ~31 full steps/sec, roughly 15-40x slower than that reference. Raising `HOME_SPEED_DEFAULT` to 3000 (still microsteps/sec) showed `SG_RESULT` peaks rising with speed (500→8, 2000→10, 4000→12, 8000→20 in a quick sweep), consistent with that theory.

**Current status:** DIAG connectivity is now confirmed correct on both axes (idle-low, as expected). Threshold tuning is still unfinished - `SGTHRS` needs to be found empirically at the new, higher home speed, and **hand-blocking the mechanism by the gear was tried repeatedly throughout this investigation and never moved `SG_RESULT` measurably**, even at reduced current - it very likely doesn't reproduce a genuine lost-step stall (a gear reduction between the finger and the motor shaft plausibly damps the reflected load far more than the direct-drive belt/carriage setups where manual-block testing is commonly reported to work). Final tuning and confirmation is deferred until the axis is mounted in the real rig and can be driven into its actual mechanical end of travel - see the tuning procedure in `README.md`.

## TMC2209 UART setup: PWMCONF/pwm_autoscale was missing

`enable_uart_mode()` configured `GCONF` (`pdn_disable`, `mstep_reg_select`, and the spreadCycle/stealthChop bit) and `set_current()` configured `IHOLD_IRUN` correctly, but neither ever touched `PWMCONF` (`0x70`). StealthChop's current-regulation loop needs `pwm_autoscale` (bit 18) and `pwm_autograd` (bit 19) enabled to actually adapt PWM amplitude to the motor/load; without them it runs open-loop off whatever `pwm_ofs`/`pwm_grad` happen to be at reset, which is rougher/louder than a properly initialized StealthChop setup. Fixed with a read-modify-write in `enable_uart_mode()` (`pwmconf |= (1<<18)|(1<<19)`) so the factory `pwm_freq`/`pwm_grad`/`pwm_ofs` defaults are left alone. Confirmed on real hardware: `PWMCONF` now reads back with both bits set after `setup_motors()`.

This doesn't affect the sensorless-homing investigation above (homing deliberately runs in spreadCycle, not stealthChop) - it's a quality-of-life fix for the *normal* bouncing/rotation moves, which do use stealthChop.

## Setup notes for the official Waveshare SDK (`STServo_Python/`)

The demo scripts in `STServo_Python/` came from Waveshare without their `scservo_sdk` dependency — it's vendored separately in `scservo_sdk/` (fetched from the official `ftservo/FTServo_Python` repo) so `sys.path.append("..")` + `from scservo_sdk import *` resolves.

Each script hardcodes `DEVICENAME` (Windows `COM*` by default) — set it to the actual device, e.g. `/dev/ttyACM0` on Linux. `ping.py`'s `BAUDRATE` was also hardcoded to `115200`, not the ST/STS-series factory default `1000000` — fixed in this repo's copy.

`ping.py` (and others) use `termios` at import time to support a "press any key" prompt, which throws `termios.error: (25, 'Inappropriate ioctl for device')` if stdin isn't a real TTY (e.g. run from a non-interactive script/CI). Run interactively, or wrap with `script -qec "python3 ping.py" /dev/null` to allocate a pseudo-terminal.

For quick command-line checks without the keypress prompt, use `STServo_Python/simple_ping.py` and `STServo_Python/simple_rotate.py`.
