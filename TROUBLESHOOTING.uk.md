# Журнал діагностики проблем

## Сервопривід ST3215: немає відповіді на шині (не вирішено — апаратна несправність)

**Симптом:** після підключення ST3215 через Waveshare Bus Servo Adapter (A) до конектора `Laser` SKR Pico (IO0/IO1, див. `PINOUT.md`), `scanner_rig.py`/`st3215.py` отримували `OSError: no reply` на кожен виклик — `ping()`, `read_position()`, `set_goal_deg()`.

**Кроки діагностики по черзі, кожен виключав щось одне:**

1. **Позиція джампера на адаптері** — підтверджено, стоїть в **A** (потрібно для UART-режиму від зовнішнього мікроконтролера, на відміну від **B**, яка перемикає на власний USB-порт адаптера). Правильно.
2. **Живлення адаптера** — світлодіод живлення на адаптері горить. Живлення підтверджено.
3. **Схрещення TX/RX** — підтверджено: TX SKR Pico (IO0) → RX адаптера, RX SKR Pico (IO1) → TX адаптера (не "напряму"). Правильно.
4. **Loopback-тест на стороні MCU** — замкнули IO0 та IO1 між собою прямо на конекторі SKR Pico (адаптер відключений), відправили сирі байти через `UART(0, tx=Pin(0), rx=Pin(1))`. Байти повернулись коректно → **апаратна частина RP2040 (піни/UART0) підтверджена повністю здоровою**, MCU повністю виключений з підозрюваних.
5. **Перебір швидкостей** — перевірено всі 9 стандартних швидкостей SC/STS (1000000, 500000, 250000, 115200, 76800, 57600, 38400, 19200, 9600) з широковісним і вузьким переборами ID. Жодної відповіді на жодній швидкості.
6. **Живлення сервопривода** — усередині сервопривода горить світлодіод, що підтверджує подачу VCC/GND на його плату керування.
7. **Заміна кабелю** — замінили кабель шини сервопривода. Без змін.
8. **Повний перебір ID сервопривода** — перебрано всі 254 можливих ID (0-253) на двох найімовірніших швидкостях (1000000, 115200) через `st3215.py`. Нічого не відповіло.
9. **Незалежна перевірка офіційним SDK Waveshare** — повністю відключили SKR Pico, підключили адаптер напряму до ПК по USB (у нього власний USB-serial чіп), завантажили офіційний `scservo_sdk` (з [ftservo/FTServo_Python](https://github.com/ftservo/FTServo_Python), тепер лежить у `scservo_sdk/`) і запустили штатний приклад `STServo_Python/ping.py`. Результат: **`[TxRxResult] There is no status packet!`** — та сама помилка, від офіційного коду Waveshare, повністю незалежно від SKR Pico, MicroPython чи `st3215.py` з цього репозиторію.

**Висновок:** власний драйвер `st3215.py` підтверджено правильний (офіційний SDK падає ідентично). SKR Pico, його GPIO-піни та підключення/схрещення/джампер — усе підтверджено справним. Несправність фізично локалізована десь у ланцюжку **адаптер ↔ кабель ↔ сервопривід** — найімовірніше, у схемі сигнальної лінії адаптера або UART-трансивері самого сервопривода, оскільки лінія живлення підтверджено робоча з обох боків (світлодіоди горять), а сигнальна лінія мовчить навіть після заміни кабелю.

**Що ще не пробували (наступні кроки, якщо питання повернеться):**
- Прозвонити мультиметром саме лінію Signal, від порту адаптера до роз'єму сервопривода.
- Підмінити сервопривід або сам адаптер на інший, якщо є — щоб локалізувати, який саме компонент несправний.
- Спробувати інший серво-порт на адаптері, якщо їх декілька.

## Нотатки з налаштування офіційного SDK Waveshare (`STServo_Python/`)

Демо-скрипти в `STServo_Python/` прийшли від Waveshare без залежності `scservo_sdk` — вона підвантажена окремо в `scservo_sdk/` (з офіційного репозиторію `ftservo/FTServo_Python`), щоб спрацював `sys.path.append("..")` + `from scservo_sdk import *`.

Кожен скрипт захардкоджує `DEVICENAME` (за замовчуванням Windows `COM*`) — виставте фактичний пристрій, наприклад `/dev/ttyACM0` на Linux.

`ping.py` (і інші) використовують `termios` вже на етапі імпорту для підтримки запиту "press any key", що кидає `termios.error: (25, 'Inappropriate ioctl for device')`, якщо stdin не є справжнім TTY (наприклад, запуск з неінтерактивного скрипта/CI). Запускайте інтерактивно, або через `script -qec "python3 ping.py" /dev/null` для виділення псевдотерміналу.
